# SEC 10-Q 引用付きQA（RAGアプリ）概要書

## 1. 概要

米国上場企業が SEC（証券取引委員会）に提出する四半期報告書「10-Q」を対象に、自然言語の質問へ答える RAG（検索拡張生成）アプリケーションです。回答には必ず根拠となる箇所（書類名・年度・四半期・セクション・引用文）を付け、根拠が見つからない質問には回答を拒否します。

初期版は 10-Q を先行対応とし、将来的に年次報告書「10-K」にも対応を広げる（§4, §8 参照）。

- 想定利用者：投資リサーチを行う個人、金融・企業分析に関わる実務者
- 位置づけ：AI Engineer 応募用のポートフォリオ作品（RAG 部門）
- 対象期間：初期版は対象企業を限定し、直近数四半期分の 10-Q を扱う

**前提（スコープ）**：SEC EDGAR からの取得・HTML/iXBRL 解析・Item 単位への構造化は、本アプリの範囲外とし、別のエージェントアプリケーション（データ取り込みパイプライン）が担う。本アプリは、構造化済みのチャンク（書類・企業・年度・Item番号などのメタデータ付きテキスト）が既に揃っている前提で、索引化・検索・回答生成・評価・UI を実装する。

## 2. 目的

- 10-Q から、知りたい情報を素早く、根拠付きで取り出せるようにする
- 「答えられないことは答えない」という拒否動作を含め、回答の信頼性を測定できる形にする
- RAG の評価（検索精度、回答の忠実性、引用の正しさ、拒否精度）を一通り実装し、数値で示す

## 3. 主な機能

| 機能 | 内容 |
|---|---|
| 質問応答 | 「A社の2025年の研究開発費は？」のような質問に回答する |
| 引用表示 | 回答ごとに、書類・年度・セクション（例：Item 7）・該当箇所の引用文を表示する |
| 拒否動作 | 根拠が見つからない場合は、推測せず「該当する記載が見つからない」と返す |
| 年度・企業の絞り込み | 企業のティッカーと会計年度で検索範囲を絞る |
| 根拠の確認 | 引用元の SEC の URL へのリンクを表示する |

## 4. 対象データ

- **データソース**：SEC EDGAR（米国政府の公開データ）。取得そのものは別のエージェントアプリケーション（データ取り込みパイプライン）の責務であり、本アプリはその出力を受け取る側
- **書類**：10-Q（四半期報告書）。将来的に 10-K（年次報告書）を追加する
- **入力データの形**：取り込みパイプラインが Part I Item 1（財務諸表）、Part I Item 2（MD&A）、Part I Item 3（市場リスクに関する質的・量的開示）、Part II Item 1（法的手続き）などのセクション単位に分割し、企業・会計年度・四半期（Q1/Q2/Q3）・Item番号などのメタデータを付与済みのチャンクとして供給する（供給形式・連携方法は別途インターフェース定義を参照）。10-K 追加時は Item 1（事業概要）、Item 1A（リスク要因）、Item 7（MD&A）、Item 8（財務諸表）などの 10-K 固有セクションにも対応する
- **ライセンス**：公開データだが、SEC の利用規約に従う（取得側の責務。本アプリは SEC EDGAR に直接アクセスしない）

## 5. システム構成

```
[データ取り込みパイプライン（別アプリ・対象外）]
    │  構造化済みチャンク（企業・年度・Item番号などのメタデータ付き）を供給
    ▼
[ベクトル索引 + キーワード索引]  ← 埋め込み生成
    │
    ▼
[検索] ── ハイブリッド検索（密ベクトル + BM25）→ リランク
    │
    ▼
[生成] ── 根拠に基づく回答 + 引用、根拠不足なら拒否
    │
    ▼
[UI / API] ── 回答、引用、SEC の URL を表示
    │
    ▼
[可観測性] ── Langfuse でトレース、トークン数、費用、レイテンシを記録
```

- **バックエンド**：Python（FastAPI）
- **デプロイ**：GCP Cloud Run（またはAWS／Azure のいずれか1つ）
- **監視**：Langfuse（トレース、費用、レイテンシ）

## 6. 評価計画

### 6.1 ゴールデンセット
- 初期 30〜50 問。各問に正解、根拠となる書類・セクション・引用箇所を付ける
- 質問の種類を分ける：
  - 単純な事実確認（例：売上高、従業員数）
  - 表の読み取り
  - 回答不能（10-Q に記載がない情報。拒否すべき質問）
  - 四半期・年度をまたぐ比較
  - 曖昧な質問
  - プロンプトインジェクションを含む質問

### 6.2 指標

| 区分 | 指標 | 内容 |
|---|---|---|
| 検索 | Recall@k、MRR、hit rate | 正しい箇所を上位に取れているか |
| 生成 | faithfulness（忠実性） | 回答が根拠に基づいているか |
| 生成 | answer relevancy | 質問に答えているか |
| 引用 | 引用の正確性 | 引用文が実際に書類内にあり、回答を支持しているか |
| 拒否 | 拒否精度 | 回答不能の質問で正しく拒否できたか |
| 運用 | p50／p95 レイテンシ、1質問あたり費用 | 実測値を記録する |

### 6.3 判定の信頼性
- LLM-as-judge を使う場合、生成に使うモデルとは別系統の判定役を使う
- 10 件程度は人手でラベルを付け、判定役との一致率を確認する

### 6.4 継続評価
- プロンプト、モデル、チャンク方式、検索方式を変えたときに評価を自動実行する
- 指標が閾値を下回った場合は失敗させる（CI で品質ゲート化）

## 7. 非機能要件・制約

- **正確性の方針**：根拠がない回答より、拒否を優先する
- **免責**：投資助言ではないことを画面に明示する
- **データの扱い**：10-Q の全文は再配布しない。表示は引用箇所に限る
- **セキュリティ**：API キーは環境変数で管理し、レート制限と利用上限を設定する
- **費用管理**：1 質問あたりの費用を記録し、月額の上限を設定する

## 8. 既知の制約・リスク

- 10-Q は HTML／インライン XBRL 形式で、解析が複雑（表の崩れ、脚注の扱い）。※解析自体は取り込みパイプライン側の制約・リスクだが、チャンクの品質（表の崩れ、脚注の分離不足など）としてこのアプリの検索・回答品質に影響するため留意する
- 数値計算（前年比・前四半期比など）は LLM が誤りやすいため、初期版では計算を行わず、引用した数値を示すにとどめる
- 対象企業を限定するため、網羅性は低い（取り込みパイプラインが対応する企業・四半期の範囲に依存する）
- 評価データが少ない場合、指標の値は推定値であり、品質の保証ではない
- 取り込みパイプライン側のメタデータ仕様・供給形式が変わった場合、索引化処理やチャンクスキーマに影響する（インターフェース定義を docs/ に別途残し、変更時はそこを更新する）
- **10-K 追加時の留意点**：10-Q と 10-K はセクション構成（Item番号の意味）が異なるため、Item番号だけでは書類種別を一意に判別できない。チャンクのメタデータに書類種別（`form_type`: 10-Q/10-K）を持たせる必要があり、索引化・検索・UIの絞り込み条件に書類種別を追加する設計変更が必要（詳細は `architect.md` 参照）

## 9. 開発の進め方（目安）

| 週 | 作業 |

| 1〜2 | ゴールデンセット作成、取り込みパイプラインが供給するチャンク形式の確認・索引化（ベクトル＋キーワード） |

## 11. 面接で説明するポイント

- なぜ 10-Q を先行対応にしたか（公開データで評価しやすい、金融で需要がある。10-K は将来対応）
- ハイブリッド検索を選んだ理由と、自分の測定による比較結果
- 拒否動作をどう評価したか、誤って答えた例とその改善
- 1 質問あたりの費用と、モデルを変えたときのトレードオフ
- 限界（対象企業が少ない、数値計算をしない）を先に説明する
